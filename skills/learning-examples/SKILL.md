# 라이브러리 학습용 예제 작성 가이드

대상: $ARGUMENTS. 엄격한 규칙이 아닌 참고 지침 — 상황에 맞게 조정한다. 단, **정확성** 항목은 예외 없이 지킨다.

## 원칙
- 프로덕션이 아닌 "읽고 바로 실행해보는" 학습용 스크립트. 파일 하나 = 기능 하나.
- API를 다 훑지 않는다. 필수·중요·자주 쓰는 기능만 고르고, 자주 하는 실수와 권장 대안은 같은 예제에서 함께 보여주고, 주석에는 "주의:"로 표시한다.
- 목차는 프로젝트 `README.md`에 유지한다.
- **간결하게**: 여러 단계에서 같은 개념을 되풀이하지 않고, 대상 라이브러리 밖의 기능(예: 기반 라이브러리 메서드) 시연은 뺀다. 데이터는 한 번 넣고 단계가 이어지게 구성해 재삽입을 피한다.
- **정확성**: 주석에 적는 라이브러리 동작(반환값, 기본값, 예외 등)은 직접 실행해 확인한 것만 쓰고, 코드를 고친 뒤(간결화 포함)에도 다시 실행한다. 단계 번호마다 주석·코드·출력 라벨이 서로 맞아야 하고, 아직 설명하지 않은 기능을 앞 단계에서 미리 쓰지 않는다. "주의:" 표시는 실제로 조심해야 할 동작에만 붙인다.

## 파일 구성
- 번호 매긴 flat 파일(`ex1.*`, `ex2.*` ...). 디렉터리로 나누지 않는다.
- 공용 준비 코드(초기화/연결/인증)와 여러 예제에서 반복되는 확인 코드는 헬퍼 하나로 분리한다.
- 생성물 이름에 예제 번호 prefix를 붙인다.
- 각 단계 주석에 "바깥에서 확인하는 방법"을 쓰고, 파일 하단에 확인 명령을 모은다.
- 삭제/정리처럼 되돌리기 어려운 동작은 주석 처리해 두고 켜서 쓰라고 안내한다.
- 쉬운 것부터, 비슷한 유형(CRUD, 조회, 인덱스, 집계 등)끼리 번호를 몰아 배치한다.

## 진행 방식
1. **계획 먼저**: 코드 작성 전에 예제 목록·순서와 각 항목이 중요한 이유(한 줄)를 제시하고 확인받는다. 20개는 상한일 뿐 목표가 아니다.
2. **단위별 피드백**: 한 개 또는 몇 개씩 작성하고, 정확성 기준으로 단계별 자체 검토를 마친 뒤 멈춰서 실행 결과를 보여주고, 피드백을 받고 다음으로 넘어간다. 피드백에 따라 기존 예제나 남은 계획을 고친다.
3. **README 목차 즉시 갱신**: 매 단위를 피드백받기 전에 목차를 갱신한다.
