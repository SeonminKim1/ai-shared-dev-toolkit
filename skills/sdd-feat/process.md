# SDD 프로세스

**[1. PRD] ➔ [2. SPEC] ➔ [3. PLAN] ➔ [4. TASK] ➔ [5. IMPLEMENT]**

언어·프레임워크와 무관한 SDD(Spec-Driven Development) 방법론입니다. 1인 백엔드 개발 기준이며, 각 단계의 목적은 "다음 단계로 넘어가도 될 만큼 정리됐는가"를 확인하는 것이지 문서를 채우는 것이 아닙니다.

## 파일 구성
`.claude/`는 `ai-shared-dev-toolkit` 서브모듈입니다. 경로는 소비 프로젝트 루트 기준입니다.

| 파일 | 구분 | 담는 내용 |
|---|---|---|
| `.claude/skills/sdd-feat/process.md` | 공통 | SDD 방법론: 단계별 기준, Grill, 문서 관리·커밋 규칙 (이 파일) |
| `.claude/skills/sdd-feat/` | 공통 | `/sdd-feat` 실행 절차(`SKILL.md`), 단계별 문서 템플릿(`templates/`), 이슈 트래커 명령(`tracker-github.md`) |
| `.claude/stacks/<stack>.md` | 스택 | 그 스택의 코드 규칙과 아래 "스택 연결 값". 같은 스택의 어느 프로젝트에도 맞는 내용만 |
| `.claude/skills/sdd-init-<stack>/` | 스택 | 새 프로젝트 생성 스킬과 기본 코드 |
| `CLAUDE.md` | 프로젝트 | 이 프로젝트에만 맞는 것: 개요, 고유 모듈, 서비스 요구사항. 스택 파일을 `@import` |
| `README.md` | 프로젝트 | 사람용: 소개, 실행 방법, 환경 변수, API 목록 |
| `docs/<feature-name>/` | 기능 | 기능 하나의 PRD~구현 기록 |

- 새 스택에 적용할 때는 공통 파일은 그대로 두고 `stacks/<stack>.md`와 `skills/sdd-init-<stack>/`만 새로 만듭니다.
- 같은 내용을 두 군데에 쓰지 않습니다. 어디에 둘지 헷갈리면: 언어와 무관하면 이 파일, 같은 스택의 다른 프로젝트에도 맞으면 스택 파일, 이 프로젝트에서만 맞으면 `CLAUDE.md`.

### 스택 연결 값
이 파일에서 스택마다 달라지는 값입니다. 스택 파일의 `## 스택 연결 값`에 모두 채웁니다.

| 항목 | 내용 |
|---|---|
| **레이어** | 레이어 규칙과 레이어별 디렉터리(안쪽 → 바깥쪽) |
| **에러 표현** | SPEC 에러 케이스에 적을 에러 식별자와 상태 코드 |
| **TASK 기본 순서** | 레이어 순서대로 나눈 작업 예 |
| **컴포넌트 구동 위치** | 백그라운드 컴포넌트를 띄우는 곳 |
| **확인 명령** | lint·format·테스트 명령 |
| **API 확인 방법** | API를 직접 호출하고 문서를 확인하는 곳 |
| **추가 완료 항목** | 스택에만 있는 완료 체크리스트 항목 |

## 한눈에 보기
기능 하나당 `docs/<feature-name>/` 폴더 하나에 아래 문서를 차례로 만듭니다. `<feature-name>`은 kebab-case에 접두사를 붙입니다: HTTP API `api-`, 화면·UI `ui-`, 백그라운드 컴포넌트 `component-`, 도메인 모델만 정의 `domain-`.

| 단계 | 답하는 질문 | 산출물 (템플릿: `.claude/skills/sdd-feat/templates/`) | 넘어가는 기준 |
|---|---|---|---|
| 0. 방향성 | 이 서비스는 무엇을 하나? | `CLAUDE.md` 요구사항 섹션 | 기능이 기존 요구사항과 충돌하지 않음 |
| 1. PRD | 왜, 무엇을 만드나? | `prd.md` | 하는 일과 규칙이 한두 문단으로 설명됨 |
| 2. SPEC | 어떻게 동작하나? | `spec.md` (접두사에 맞는 템플릿: `api-` → `spec-api.md`, `ui-` → `spec-ui.md`, `component-` → `spec-component.md`, `domain-` → `spec-domain.md`) | 템플릿 항목이 빠짐없이 채워짐 |
| 3. PLAN | 코드 어디를 바꾸나? | `plan.md` | 레이어별 변경 파일과 DB 변경이 정리됨 |
| 4. TASK | 어떤 순서로 하나? | `task.md` | 작업 크기·순서·병렬 묶음을 사용자가 확인함 |
| 5. IMPLEMENT | 제대로 동작하나? | 코드 + `implement.md` | 완료 체크리스트 통과 |

진행은 `/sdd-feat` 스킬로 합니다(사용법: `.claude/skills/sdd-feat/SKILL.md`). 한 단계의 문서를 만들면 보여주고 확인받은 뒤 다음 단계로 갑니다. **spec 없이 구현하지 않습니다.**

### 문서 관리 규칙
| 문서 | 수정 방식 | 이유 |
|---|---|---|
| `prd.md`, `spec.md` | 항상 현재 상태로 **덮어쓰기** | 지금의 기준 문서 |
| `plan.md`, `task.md`, `implement.md` | 아래에 `## 변경: YYYY-MM-DD <요약>` 섹션 **추가** | 작업 이력 보존 |

구현 중 spec과 달라진 점은 `implement.md`에 남기고 `spec.md`도 고칩니다.

### Grill 규칙
각 단계에서 Claude는 문서를 쓰기 전에 그 단계의 **Grill 체크리스트**로 허점을 점검합니다.

1. **점검과 질문을 나눈다.** 코드·문서·`CLAUDE.md`로 답이 나오는 것은 묻지 않고 결정하며, 문서에 근거를 적습니다. 질문은 Claude가 정할 수 없는 것(비즈니스 판단, 트레이드오프)에만 씁니다.
2. **틀렸을 때 비용이 큰 순서로 묻는다.** 되돌리기 어려운 것(데이터 구조, 공개 API 형태) → 보안·권한·데이터 손실 → 비즈니스 규칙 해석 → 나머지.
3. **한도를 넘은 질문은 버리지 않는다.** 가정과 함께 문서 끝 `## 확인 필요`에 남깁니다.

질문 한도: PRD 3개(기능의 방향) / SPEC 5개(엣지 케이스·에러, 가장 힘을 주는 단계) / PLAN 3개(설계 대안) / TASK 1~2개(작업 계획 검증) / IMPLEMENT 0개.

**되돌아가기**: 구현 중 spec·plan이 다루지 않는 상황을 발견하면 추측으로 메우지 않습니다. 멈추고 질문한 뒤, 해당 문서를 먼저 고치고 구현을 이어갑니다.

### 작은 변경은 단계를 줄인다
- **버그 수정 / 문구·로깅 수정**: 바로 5단계. 문서 폴더가 있으면 `implement.md`에 한 줄 남깁니다.
- **기존 기능의 동작 변경**: `spec.md`를 고친 뒤 3~5단계. PRD는 규칙이 바뀔 때만 수정합니다.
- **새 API·새 컴포넌트**: 1단계부터 모두.

## 0. 방향성 (필요할 때만)
서비스의 큰 방향이 바뀌는 결정(인증 방식, 쿼터 정책, 외부 노출 방식 등)은 기능 PRD보다 먼저 사용자와 논의하고, 결론을 `CLAUDE.md`의 요구사항 섹션에 반영합니다.

## 1. PRD — 왜 / 무엇을
- 거창한 KPI 대신 **"이게 되면 끝"을 완료 기준 한 줄**로 적습니다. 구현 디테일(Method/Path, 필드 타입, 상태 코드)은 적지 않습니다.

**Grill 체크리스트**
- 이 기능이 없으면 무엇이 안 되는가? 완료 기준이 검증 가능한 문장인가?
- 범위 제외가 비어 있지 않은가? (범위가 너무 크지 않은가)
- `CLAUDE.md` 요구사항이나 다른 기능과 충돌하지 않는가?
- 이 기능에만 해당하지 않는 규칙이 섞여 있지 않은가? 있으면 확인 후 `CLAUDE.md` 요구사항으로 옮기고 PRD에는 참조만 남긴다.

## 2. SPEC — 어떻게
- `<feature-name>` 접두사에 맞는 템플릿 하나를 씁니다(위 표). 예외 케이스는 "에러 케이스"에 스택 연결 값의 **에러 표현**으로 적습니다.
- PRD에 없는 디테일(Method/Path, 필드 타입, 상태 코드, 실행 방식 등)은 추측하지 않고 질문합니다. 기존 `docs/*/spec.md`의 패턴(에러 코드, 응답 형태)을 맞춥니다.

**Grill 체크리스트**
- 경계값: 0, 음수, 최대값, 빈 문자열·빈 목록, 누락된 필드
- 권한: 다른 유저의 리소스에 접근하면? 식별자가 없거나 잘못되면?
- 동시성·멱등성: 같은 요청이 동시에, 또는 여러 번 오면?
- 외부 의존 실패: DB·외부 시스템이 느리거나 실패하면?
- 상태 전이: 이미 삭제·완료된 리소스에 요청하면?
- 모든 에러 케이스에 에러 식별자와 상태 코드가 있는가?

## 3. PLAN — 코드 어디를 바꾸나
**Grill 체크리스트**
- 스택 연결 값의 **레이어** 규칙을 어기는 곳이 없는가?
- DB 인덱스·유니크 제약·기존 데이터 마이그레이션이 필요한가?
- spec의 동시성·실패 케이스를 코드에서 어떻게 지키는가? (락, 유니크 인덱스, 트랜잭션 등)
- 더 단순한 대안은 없는가? 되돌리기 어려운 결정이나 기존 기능에 주는 영향이 있는가?

## 4. TASK — 어떤 순서로
- 작업 하나는 **반나절~1일 크기**로, `T<번호> [기능명] 작업 내용` 형식으로 씁니다.
- 작업마다 **선행 작업**을 적고, 이를 바탕으로 **실행 흐름**(순차/병렬 단계)을 만듭니다. 기본 순서는 스택 연결 값의 **TASK 기본 순서**(레이어 안쪽 → 바깥쪽)입니다.
- `task.md`를 쓴 뒤 실행 흐름을 보여주고 작업 계획 검증 질문 1~2개를 합니다(크기·순서, 병렬 묶음, 빠진 작업). 사용자가 확인해야 IMPLEMENT로 넘어갑니다.

**Grill 체크리스트**
- 하루를 넘는 작업이 없는가? 선행 관계가 실제 코드 의존과 맞는가?
- 테스트 작업과 문서 갱신 작업이 빠지지 않았는가?

### 이슈 트래커 연동
`CLAUDE.md`에 이슈 트래커가 설정돼 있을 때만 합니다(없으면 건너뛰고 알림). 트래커별 명령은 `.claude/skills/sdd-feat/`에 둡니다(GitHub: `tracker-github.md`).

| 시점 | 할 일 |
|---|---|
| TASK 확인 후 | 이슈가 없는 작업마다 이슈 생성(담당자 본인), 보드에 `Todo`, `task.md`에 이슈 번호 기록 |
| 작업 시작(▶) | 상태 `In Progress` |
| 작업 확인·커밋 후 | 상태 `Done`, 이슈 닫기(결과 한 줄 코멘트) |
| IMPLEMENT 완료(리뷰 후) | 기능 브랜치 push, PR 생성(담당자 본인, 보드에 추가). 머지는 사용자 |
| 기존 기능 수정 | `task.md` 변경 섹션에서 새로 생긴 작업만 이슈 생성 |

트래커 명령이 실패해도 구현은 멈추지 않습니다. 보고하고 `implement.md`의 `## 메모`에 남깁니다.

## 5. IMPLEMENT — 구현과 확인
- **브랜치**: `main` ➔ `feature/<feature-name>`, 끝나면 `main`에 머지합니다.
- **커밋**: 작업 하나 = 커밋 하나. 히스토리만 보고도 작업 흐름을 따라갈 수 있게 합니다.
  - IMPLEMENT 시작 전: `docs(<feature-name>): PRD·SPEC·PLAN·TASK` (`CLAUDE.md` 요구사항 변경 포함)
  - 작업 확인 후: `feat(<feature-name>): T<번호> <작업 요약> (#<이슈 번호>)`. 문서만 바꾸면 `docs(...)`, 이슈가 없으면 `(#번호)` 생략.
  - 그 작업의 코드·테스트와 작업 중 고친 `spec.md`·`implement.md`를 함께 넣습니다. `task.md` 체크는 마지막 작업 커밋에서 합니다.
  - 커밋 전에 스택 연결 값의 **확인 명령**이 통과해야 합니다.
- **리뷰·머지**: 머지 전에 `/code-review`로 셀프 리뷰를 하고, 반영 후 PR을 만듭니다. 머지는 사용자가 하며, 작업별 커밋이 남도록 일반 머지를 씁니다(squash 금지).

**진행 보고**: `task.md`의 실행 흐름 단계마다 짧게 보고하고, 같은 내용을 `implement.md`의 `## 진행 기록`에 남깁니다.
- `▶ 2단계 (병렬) T2, T3 시작 — <무엇을 왜 하는지 한 줄>`
- `✔ T2 완료 — 바뀐 파일, 테스트 결과, 특이사항`
- `■ 2단계 완료 — 다음: 3단계 T4 (<한 줄>)`
- `⏸ T4 중단 — spec에 없는 상황: <내용>` 후 질문(되돌아가기)

**작업 확인**: 사용자가 흐름을 따라가며 학습할 수 있도록, 작업 하나를 끝낼 때마다 멈추고 아래를 보여준 뒤 확인을 받습니다. 병렬 단계도 하나씩 진행합니다. 확인 전에는 다음 작업을 시작하지 않고 이슈도 닫지 않습니다.
- **바뀐 파일**(파일별 한 줄), **핵심 코드**(리뷰할 부분만 발췌, `파일경로:줄번호`)
- **왜 이렇게 했나**(근거가 된 규칙·spec 항목, 고려한 대안), **확인 결과**(테스트, 직접 실행)
- **봐 줄 것**(사용자 판단이 필요한 부분, 없으면 생략)

**Grill 체크리스트** (질문하지 않음)
- spec의 에러 케이스마다 테스트가 있는가? spec과 달라진 점이 기록됐는가?
