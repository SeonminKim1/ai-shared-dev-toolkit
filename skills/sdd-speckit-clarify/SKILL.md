# /sdd-speckit-clarify

시작 전에 읽는다: `CLAUDE.md`, `.claude/skills/sdd-speckit/process.md`, `.claude/skills/sdd-speckit/constitution.md`, 스택 파일의 "스택 연결 값". 대상 기능은 process.md "기능 디렉터리"대로 찾는다. `spec.md`가 없으면 `/sdd-speckit-specify`를 안내하고 멈춘다.

## 1. 점검
spec을 아래 분류로 훑어 각각 명확 / 부분 / 없음으로 판정한다(내부용, 질문이 없을 때만 표로 보여준다). 인자로 집중할 부분을 받았으면 그것부터 본다.

| 분류 | 볼 것 |
|---|---|
| 기능 범위 | 핵심 목표·성공 기준, 범위 제외, 사용자 역할 구분 |
| 도메인·데이터 | 엔티티·속성·관계, 식별·유일성, 상태 전이, 데이터 규모 |
| 상호작용 흐름 | 주요 흐름 순서, 에러·빈 결과 상태 |
| 비기능 | 성능, 확장 한계, 신뢰성·복구, 관측(로그·지표), 보안·권한 |
| 외부 연동 | 외부 시스템과 실패 방식, 입출력 형식 |
| 엣지 케이스 | 경계값, 권한(남의 리소스), 동시성·중복 요청, 외부 실패, 이미 삭제·완료된 상태, 스택 연결 값의 엣지 케이스 |
| 제약·트레이드오프 | 기술 제약, 버린 대안 |
| 용어 | 같은 개념을 다른 이름으로 부르는지 |
| 완료 신호 | 인수 시나리오가 테스트 가능한지, 모호한 형용사("빠르게", "안정적") |

코드·문서·`CLAUDE.md`로 답이 나오면 묻지 않고 spec에 반영하고 근거를 적는다. 구현 방법·기술 비교·작업 분할은 묻지 않는다(plan·tasks 몫).

## 2. 질문 (최대 5개, 한 번에 하나)
- 영향 × 불확실성이 큰 순서(process.md "질문 규칙")로 고른다. 다음 질문을 미리 보여주지 않는다.
- AskUserQuestion으로 묻는다. 질문은 그 자체로 이해되는 의문문, 바로 뒤에 "왜 중요한지" 한 문장. 선택지 2~4개, 추천안을 첫 번째에 `(Recommended)`와 이유로 둔다.
- 사용자가 "그만", "됐어"라고 하거나 중요한 빈틈이 다 풀리면 멈춘다. 5개를 넘은 중요한 빈틈은 `## 확인 필요`에 가정과 함께 남긴다.

## 3. 답마다 바로 반영
1. spec의 `## 개요` 아래에 `## 명확화` → `### 세션 YYYY-MM-DD`를 만들고(있으면 이어서) `- Q: <질문> → A: <답>`을 추가한다.
2. 해당 섹션을 고친다: 기능 → 기능 요구사항, 역할·흐름 → 유저 스토리, 데이터 → 핵심 엔티티, 비기능 → 성공 기준(측정 가능한 값으로), 예외 → 엣지 케이스, 용어 → spec 전체에서 하나로 통일.
3. 답과 어긋나는 이전 문장은 남기지 않고 바꾼다. 관련 없는 섹션 순서는 건드리지 않는다. 답마다 저장한다.

## 4. 마무리
1. `checklists/requirements.md`가 있으면 항목을 다시 판정하고 바뀐 체크만 토글한다.
2. 보고: 질문 수, 고친 섹션, 분류별 결과(해결 / 보류 / 남음), 체크리스트 통과 수 변화(예: 12/15 → 15/15).
3. 다음 안내: `/sdd-speckit-plan`. 남은 빈틈이 크면 clarify를 한 번 더 권한다.
