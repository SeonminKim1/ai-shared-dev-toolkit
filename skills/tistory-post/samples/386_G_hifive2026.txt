<h2>Tech 세미나
<p>**주제 : AI 시대에도 커리어가 계속 쌓이는 엔지니어의 비밀**
<p>**발표자 : 이승준 / Apple **

  - 좋은 문제 정의자가 되는 것이 가장 중요하다.
  - 코드는 나중 plan을 먼저 세운 후 작업해라
  - document를 LLM wiki를 구축해, 팀의 질문과 업무 맥락이 자연스럽게 축적되고 검색 될 수 있도록, 문맥을 문서로 남길 수 있는 개발자가 되어라
  - 아침에 일어나 어제의 일과와 오늘의 흐름을 정리하며 하루를 예측하는 personal assistant 루틴을 만든다.
  - 오래가는 사람은 결국 의지가 아니라 시스템을 가진 사람이다.
  - 주니어 3가지 명심사항<br>- 문제를 잘개 쪼개는 능력 (내가 어디서 막히었는가)<br>- 좋은 질문을 던지고 끊임없이 의심하는 태도<br>- 남에게 설명할 수 있는 수준의 이해력이다.
  - 다음 스프린트를 미리 준비하고 사전에 검증해보는 과정(미리 맞아보기)이 중요하다.
  - 코드 검증 범위를 명확히 설정하고, 부모 위키 기반으로 테스트 하네스를 구성하며 unittest로 테스트 케이스를 구축한다.
  - md 문서는 점점 방대해지기 때문에, 최대한 작은 단위로 분리하여 lazy loading 처럼 컨텍스트 오염을 최소화해야 한다.
  - 어떤 문서를 남기고 어떤 문서를 삭제할지는 직접 관리하기보다 배치 방식으로 정리하는 것이 효율적이다.
  - R&R 경계 넘나드는 사례에 대한 의견 : 대기업에서는 R&R 경계를 넘나드는 일이 상대적으로 적고 역할이 명확하게 분리되어 있다.
  - 트렌드는 계속 변하지만 펀더멘탈(개발의 본질적인 역량과 원리)은 바뀌지 않음

<p>**주제 : 토스 프론트엔드, 1명부터 260명까지. 앞으로는? **
<p>**발표자 : 박서진, 한재엽 / 비바리퍼블리카**

  - 프론트엔드 조직이 1명 → 260명으로 성장하며, “일관된 확장”이 핵심 과제가 됨.
  - 잘하는 사람도 더 잘하기 위해 코치가 필요함. (메타인지, 큰 그림, 방향성 보정)
  - 국가대표에도 코치는 있다 / (잘하는데 있으면 더 잘한다, 메타인지 상승 등)
  - 리더의 역할은 실무보다도 “큰 그림 정렬”에 가까워짐. (업무 완료 보고 등 안받음)
  - 플레잉 코치의 코치까지 필요한 구조로 확장됨.
  - 개개인의 시간을 아끼기 위해 플랫폼을 만들어 운영한다.
  - 코드리뷰 단계에서 5개의 AI Agent를 활용
  - AI 활용도 개인 역량보다 조직 차원의 표준화로 이동 중.
  - 개발자가 직접 Skill 쇼핑하지 않아도 최신 활용법이(팀원)에 의해 플랫폼에 반영됨.
  - Claude 활용 방식도 중앙 조직(Tab39 위원회 등)에서 지속 업데이트.
  - PRD는 .md 더 있고 디자인 문서일수도 있고
  - 260명이나 있는 이유는. 모-든-걸 다 만들기 때문에
  - 결국 방향성은 “일관된 개발 인원 확장”.

<p>**주제 : Inside Out: Agent Platform 개발기 **
<p>**발표자 : 정기수 / 원티드랩**
<p>**자료 : <a https://www.linkedin.com/posts/%EA%B8%B0%EC%88%98-%EC%A0%95-92596381_agent-platform-%EA%B0%9C%EB%B0%9C%EA%B8%B0-ugcPost-7460236826352566272-oroi?utm_source=share&utm_medium=member_desktop&rcm=ACoAAC34pP4B8hd_cAU7P9YigaaYkFVicHujf38>링크</a>**

  - LLM 기반 플랫폼, RAG 기반 플랫폼, Agent Builder 플랫폼 등을 직접 구축한 사례를 공유
  - 데이터를 잘게 구조화하고 적절한 input으로 연결하는 능력이 중요하며, 이를 통해 지식 검색 품질이 크게 향상된다.
  - 기업 내부 데이터를 지식 구조로 정리해 내부 사용자들이 AI 제품을 자연스럽게 활용할 수 있도록 만드는 것이 핵심
  - UI 자체보다 내부 데이터 구조와 Agent 동작 구조를 설계하는 역량에 더 집중한다.
  - Agent의 오답 여부, 권한 범위, 행동 로그 등을 지속적으로 모니터링하며 피드백 루프를 관리해야 한다.
  - 고객 확장에서 중요한 것은 단순 기능 추가보다 데이터 구조화와 입력 설계였다.
  - 실제 운영에서는 데이터 권한 관리 이슈가 생각보다 훨씬 중요했고, 많은 부분을 커스터마이징으로 해결했다.
  - 전체 방향은 단순 SaaS보다는 “기업 내부 업무 패키지”와 고도화된 Admin 플랫폼에 가까운 형태다.
  - 핵심 지표는 단순 생성된 Agent 수가 아니라, 지속적으로 운영되고 고도화되는 Agent 수다.
  - 대화형으로 생성된 결과를 다시 구조화된 View 형태로 검증하는 과정이 중요하다.
  - 결국 기업 내부의 AX(AI Transformation) 전환을 촉진하는 플랫폼을 만드는 방향이다
  - 미래 방향은 Hyper Agent 기반으로 운영 개선 체계를 더욱 탄탄하게 만드는 것이다.
  - Agent가 읽을 수 있는 Knowledge Layer와 중앙집중형 LLM Wiki 구조가 매우 중요하다.
  - 지식을 잘 축적하고 연결해 플랫폼 형태로 운영해야 한다.
  - 조직 내에서 Agent가 어떤 역할과 정책으로 운영되어야 하는지까지 설계해야 한다.
  - 자가 개선(Self-improving) 워크플로우 구조가 핵심 방향 중 하나다.
  - 기업 환경에서는 정책, 권한, 거버넌스 설계가 특히 중요하다.
  - 플랫폼을 만드는 과정에서 가장 어려운 점 중 하나는 시장의 기대 수준을 맞추는 일이었다.
  - 결국 플랫폼 구축은 체력 싸움에 가까운 지속적인 운영과 개선 과정이다.
  - 실제로 지속 운영되는 Agent 플랫폼이 존재하는지가 플랫폼 성공의 중요한 지표다.
  - 앞으로는 사람이 직접 '운영'하는 시간이 줄고, Agent들이 운영 업무를 점점 더 많이 수행하게 될 것이다.
  - 기업 내 AX 전환을 촉진하기 위해서는 공유 문화와 동기부여 체계가 중요하다.
  - 전사 채널 공유, 매달 시상, 후속 활동 장려 등을 통해 AI 활용 문화를 확산시킨다.
  - 비용 최적화를 위해 멀티 에이전트 구조로 저가 모델과 고성능 모델을 적절히 혼합 사용한다.
  - 핵심 방향은 AI 기반의 전사 워크플로우 최적화다. 이를 위해 누구나 직접 AI Agent를 만들 수 있는 환경을 제공해야 한다.
  - Vibe Infra는 비개발자도 보안이 격리된 샌드박스 환경에서 쉽게 개발할 수 있도록 만드는 개념이다.
  - 인프라 설정 부담을 플랫폼이 대신 처리해 개발 경험을 단순화한다.
  - 누구나 서비스를 만들 수 있게 되면서 전체 서비스 생성량 자체가 증가하게 된다.
  - 동시에 중앙집중형 관리 구조를 통해 안정성과 운영 효율도 확보한다.
  - 궁극적인 목표는 일관성 있게 확장 가능한 플랫폼 구조를 만드는 것이다.
  - AI 결과물은 까나리(Canary) 방식으로 점진 검증 및 단계적 적용을 수행한다.
  - 수천 줄 규모의 PR도 AI와 플랫폼 기반으로 리뷰 효율화를 진행한다.
  - 특히 안정성을 위해 E2E 테스트를 매우 강하게 반복 수행한다고 한다.
  - 기업 내에서 비용 최적화할 때 멀티에이전트로 싼 모델들 비싼 모델들 사용

<p>**주제 : 레트로 지향 엔지니어의 AI시대 적응기 **
<p>**발표자 : 정찬훈 / 센드버드**

  - Anthropic의 Claude는 여러 작업 흐름을 하나의 메모리처럼 통합해 기억하는 특성이 있다.
  - 실제 작업 시 체감상 워크트리를 3개 정도로 분리해서 작업했고,  원래라면 각각의 워크트리는 서로 다른 문맥과 메모리를 가져야 하지만, Claude는 이를 하나의 연속된 기억처럼 합쳐 처리하는 경향이 있었음.
  - 그 결과 과거에 잘못 이해했거나 실패했던 맥락이 이후 작업에서도 반복적으로 다시 등장하는 문제가 발생했다.
  - 즉, 메모리 통합이 항상 장점만 있는 것은 아니며, 문맥 분리(Context Isolation)의 중요성이 함께 드러난 사례였다.
  - AI 시대에는 단순히 “기억을 많이 하는 것”보다, 어떤 기억을 어떻게 분리하고 관리할지가 점점 더 중요해지고 있다.

<h2>UX / UI 세미나
<p>**주제 : AI 페르소나, 어떻게 하면 믿을 수 있을까요? **
<p>**발표자 : 양희연, 이호동 / 네이버**
<p>**자료 : <a https://dan.naver.com/25/sessions/699>링크</a>**

  - AI를 단순 도구가 아니라, 가상의 디자이너·개발자 페르소나와 함께 협업하는 팀원처럼 사용하는 UX를 지향했다.
  - 실제 사람과 함께 일하는 것과 유사한 협업 경험(UX)을 만드는 것이 핵심 목표였다.
  - ex) 4명의 팀에서의 회의록이 기획자, 디자이너, pm, 백엔드 개발자 역할의 AI 팀을 구성해 회의록 기반 협업을 실험했다.
  - AI 신뢰도 평가가 매우 중요 기존 대화나 보고서에 대한 비평을 다시 수행하게 하여 LLM 기반 점수 체계로 측정
  - **사람은 일반적으로 능력이 보일 때, 나에게 실제 도움이 될 때, 일관된 원칙을 지킬 때 신뢰를 형성하고, 동료를 믿기 시작한다.**
  - **모델의 언어 능력(발화 능력)이 뛰어난 것과, 실제 프로젝트와 서비스에 도움이 되는 것은 별개의 문제였다.**
  - 단순 모델 성능뿐 아니라, 실제 협업 상황 전체에 대한 효과성과 신뢰성을 함께 평가했다.
  - 책임감과 협업 태도, 강한 비판 상황에서의 반응도 중요한 평가 요소였다.
  - 결국 핵심은 “이 AI를 정말 팀원처럼 받아들일 수 있는가”에 대한 질문이었다.
  - **Solo Founder 관점에서 AI 팀원을 구성해보았지만, 아직은 실제 동료 수준에는 부족함이 있었다.**
  - 원하는 협업 스타일과 결과 품질을 Persona 설계를 통해 조정(세밀하게 튜닝하면)할 수 있다는 가능성(통제가능)을 확인했다.
  - **UX 관점에서는 AI의 말투와 캐릭터(Persona)가 매우 중요한 요소로 작용했다.**
  - 긍정적이고 공감적인 발화를 가진 Persona는 아이디어 발산형 대화에서 높은 평가를 받았다.
  - 반면 합의와 조율이 필요한 수렴형 대화에서는 다소 약하거나 회피적인 태도를 보였다.
  - **기존 HCI(Human-Computer Interaction)는 시각적 UI 중심이었지만, 이제는 “대화를 통한 경험” 자체도 중요한 UX 요소로 본다.**
  - 고객 Persona를 만들 때는 실제 사용자 인터뷰 데이터와 서브 데이터를 함께 활용했다.
  - **Persona가 실제 사용자와 지나치게 달라지지 않도록 다양한 가이드와 제약을 지속적으로 주입했다.**
  - “LLM as a Judge” 기반 평가 결과가 실제 사용자 반응 데이터와 얼마나 상관관계가 있는지도 중요한 연구 주제였다.
  - 내부에서 Persona 시스템이 얼마나 활용되고 있는지는 보안상 자세히 공개되지 않았다.
  - **기존에 정의된 Persona 외에도 다양한 유형과 역할을 조합해 새로운 Persona를 확장 가능하게 생성할 수 있도록 설계했다. -> B2B / 내부 팀 공유**
  - 사용자가 직접 결과를 피드백받고 Persona 학습 방향을 조정할 수 있도록 하는 구조도 함께 고려했다.
